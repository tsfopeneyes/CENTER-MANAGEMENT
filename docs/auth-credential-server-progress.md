# 초기화·임시 비밀번호 변경 서버 진행 기록

## 적용 범위

2026-09-01 현재 로컬 격리 구현이다. 운영 DB, 계정, 기존 화면, 배포에는 적용하지 않았다.
`supabase/manual/proposals/auth-credential-foundation.sql`은 검토용 SQL이며 migration이 아니다.

## 확정한 동작

- 관리자가 기존 방식대로 이용자를 직접 확인한 뒤 서버에 등록된 전화번호 뒤 4자리를 임시값으로 발급한다.
  별도 회원 승인이나 MFA 절차는 추가하지 않는다.
- 네 자리는 Supabase Auth 비밀번호로 설정하지 않고 일반 로그인 세션도 발급하지 않는다.
  전용 비밀번호 변경 요청 한 번에만 사용할 수 있다.
- 원문 네 자리, 전화번호, 토큰, 신분 확인 자료는 DB와 작업 기록에 저장하지 않는다.
  전용 private 테이블에는 운영용 `passwordHasher`가 만든 digest만 저장한다.
- 네 자리는 경우의 수가 작으므로 각 값별 salt와 DB 밖의 비밀 pepper가 필수다.
  `temporaryCredentialHasher.mjs`는 Web Crypto의 HMAC-SHA-256과 PBKDF2-SHA-256을 사용하고 비용·형식 범위를
  제한한다. pepper는 코드나 DB에 저장하지 않으며 운영 secret 연결은 아직 하지 않았다.
- 관리자 권한, 유효한 일회성 본인 확인 기록, 대상 계정과 현재 등록 전화번호는 모두 서버에서 확인한다.
  요청 본문의 역할이나 전화번호 주장은 신뢰하지 않는다.
- 관리자 요청의 bearer session은 공통 권한 검사로 확인하고, 본인 확인 기록은 관리자 프로필·대상 프로필·목적·
  만료 시각에 묶는다. 브라우저에는 전화번호나 digest를 반환하지 않는다.
- 같은 본인 확인 기록은 DB UNIQUE 제약으로 다시 사용할 수 없다. 계정별/요청 출처별 시도 제한과
  자격 버전 검사를 적용한다.
- 임시값이 맞고 새 영구 비밀번호가 제공자 정책을 통과한 경우에만 Supabase Admin API로 영구 비밀번호를
  한 번 변경한다. 성공 후 임시값은 자격 버전이 달라져 즉시 무효가 되고 사용자는 새 비밀번호로 로그인한다.
- 로그인 상태에서 평상시 비밀번호를 바꾸는 경로는 현재 bearer session과 본인 프로필을 확인하고 자격 버전을
  올린 뒤 새 비밀번호로 만든 세션을 다시 검증·assurance 등록한다. 브라우저는 검증된 교체 세션을 제자리에서
  적용하므로 정상 성공 시 현재 화면을 유지한다. 변경 요청 전 실패는 기존 세션을 건드리지 않는다.
- 임시 유효기간은 반드시 서버 설정으로 지정한다. 허용 범위는 1분~30일이고 테스트값은 10분이다.
  운영값은 이용자가 센터에서 재설정한 뒤 변경할 시간을 고려해 전환 전 확정한다.
- 공개 회원 원본과 원시 로그는 수정하지 않는다. worker는 NOLOGIN이고 공개 회원/Auth 테이블 수정 및
  작업 기록 삭제 권한이 없다. 브라우저 역할은 private 테이블에 접근할 수 없다.

## 오류 복구 경계

관리자 초기화는 native Auth를 호출하지 않으므로 네 자리를 Auth 비밀번호로 쓸 때 생기던 분산 변경을 제거했다.
초기화 예약 후 DB 완료가 실패하면 계정은 차단되고 pending 작업이 남는다. 원문 네 자리는 복구할 수 없으므로
기존 작업의 종료를 확인한 뒤 새 본인 확인 기록으로 다시 초기화해야 한다.

영구 비밀번호 변경은 Auth와 PostgreSQL 사이 원자적 트랜잭션이 불가능하다. Auth 응답 유실이나 DB 완료 실패 시
계정을 차단하고 pending 작업을 남기며 자동 재시도하지 않는다. 운영 복구 도구는 현재 Auth 상태와 자격 버전을
다시 확인하고 별도 감사 기록을 남겨야 한다. 테스트에서 상태를 직접 고치는 코드는 fixture 전용이다.

## 활성화 전 필수 조건

1. 운영 secret에서 32바이트 이상 pepper를 주입하고 KDF 비용을 실제 Edge 부하에서 검증한다.
2. 본인 확인 기록을 생성하는 기존 관리자 동작을 별도 감사 writer에 연결. 읽기 검증 모듈과 최소 권한 SQL은 준비됐다.
3. 전용 임시값 변경 HTTP 경로의 실제 Edge 진입점과 관리자/이용자 기존 화면 연결. 공통 handler의 origin,
   bearer 전달, 요청 크기·시간 제한과 클라이언트 전송 모듈은 준비됐다.
4. 모든 데이터 API와 RLS의 계정 상태·자격 버전 강제 후 기존 취약 발급 경로 종료. 이전 JWT는 버전 증가만으로
   없어지지 않으므로 이 조건 전에는 새 경로를 활성화하면 안 된다.
5. pending 작업 복구 도구, 다중 연결 PostgreSQL·Edge·실제 Supabase 시험, 백업 복원 리허설.
6. 가입 및 평상시 영구 비밀번호는 2026-09-01 사용자 결정에 따라 최소 6자로 맞춘다. 기존 회원의 현재
   비밀번호를 준비 단계에서 일괄 변경하거나 강제 로그아웃하지 않는다.

## 검증

`node scripts/test-credential-service.mjs`는 실제 제안 SQL과 worker 권한을 PGlite에서 실행해 다음을 확인한다.
네 자리가 native Auth에 기록되지 않음, private digest만 저장, 원문 비밀이 작업 기록에 없음, 만료·오입력·재사용
거부, 영구 비밀번호 변경 후 epoch 무효화, 동시 변경 경쟁, Auth 응답 유실 및 DB 완료 실패 시 차단, 연결 반환,
브라우저 역할 접근 거부, 공개 회원 데이터 보존.

Supabase Auth, 관리자 확인, 정책, 시도 제한, hasher는 테스트 대역이다. 운영 변경과 배포는 없다.
