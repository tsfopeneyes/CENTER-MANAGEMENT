# 프로필 저장 내부 경로 — 격리 구현, 운영 미연결

사용자 기준: 기능·화면·운영 절차를 바꾸지 않고 보안과 안정성만 개선한다.

## 구현

- `profileUpdateService.mjs`: 검증된 Auth 사용자와 실제 DB 세션, 계정 연결,
  인증 버전을 UPDATE 조건에서 함께 확인한다. 클라이언트가 보낸 대상 ID만으로 권한을 인정하지 않는다.
- 학교·교회·소개글·스쿨처치 여부만 명시적으로 수정한다. 학교 정규화는 현재
  `userApi`가 사용하는 `userUtils.normalizeSchoolName`의 동작을 유지한다.
- 스쿨처치 여부는 DB의 최신 preferences 객체에서 해당 키만 합친다.
  약관·알림 등 다른 설정을 과거 클라이언트 사본으로 덮어쓰지 않는다.
- 현재 화면에 없는 200/2,000자 제한을 준비 코드에서 제거했다.
  HTTP 요청 자원 제한의 호환성은 실제 라우트 연결 전에 별도로 확인해야 한다.
- 저장 중 실패·취소는 트랜잭션을 롤백한다. COMMIT 응답 유실은 결과가 불확실하므로
  자동 재시도하지 않는다. 동시 권한 철회에 대한 직렬화까지 보장하는 구현은 아니다.
- SQL 제안은 기존 users RLS 활성화를 요구하고 서버 전용 NOLOGIN 역할에
  필요한 열만 허용한다. 기존 광범위 정책과 함께 있어도 해당 역할의 행 범위를 제한한다.
  이 제안은 기존 anon/authenticated 접근 취약점을 해결하는 전체 RLS 전환이 아니다.

## 호환성 경계

| 현재 저장 항목 | 이번 준비 상태 |
| --- | --- |
| 학교·교회·소개글 | 기존 값 처리 유지, 서버 수정 경로 테스트 완료 |
| 스쿨처치 설정 | 다른 preferences 키 보존 테스트 완료 |
| 프로필 사진 업로드·URL 저장 | 기존 경로 유지, 새 서비스에 미연결 |
| 같은 화면의 비밀번호 변경 | 기존 경로 유지, 새 서비스에 미연결 |
| 관리자·스태프의 회원 관리 | 기존 권한 범위 대조 및 별도 서버 작업 필요 |

전체 저장 버튼을 이 부분 서비스로 교체하지 않았다. 사진·비밀번호 저장까지 검증된
통합 경로가 준비되기 전에는 연결하면 안 된다. 초기화 MFA·만료·변경 강제 등의
실험 조건도 이번 구현으로 채택하거나 운영에 적용하지 않았다.

## 검증

`node scripts/test-profile-update-service.mjs`는 PGlite의 실제 PostgreSQL 쿼리·역할로
본인 수정, 타인 수정 거부, 권한/비밀번호 주입 거부, 다른 설정 보존,
기존 길이 입력, 계정 차단/버전 변경/세션 삭제, 실패·취소 롤백과 연결 반납을 확인한다.
Supabase Auth 검증 응답은 모의 객체이며 실제 다중 연결 경합·운영 SDK 통합 검증은 아니다.
권한·가입 폼·회원 저장·클라이언트 로그인·서버 로그인·세션·비밀번호 코어의
기존 테스트 7개도 통과했다. 실험 코어 테스트 통과는 해당 운영 정책의 채택을 뜻하지 않는다.

이번 작업은 로컬 준비 코드와 SQL 제안·테스트·문서만 변경했다.
추가 운영 DB 변경, 배포, 로그아웃, 회원 데이터 수정은 실행하지 않았다.
전체 인증 전환 및 기존 공개 CRUD/RPC 경로 정리는 아직 완료되지 않았다.

## 후속: 기존 저장 코드 회귀 검증과 캐시 오류 수정

`scripts/test-profile-save-compatibility.mjs`는 실제 ProfileSettingsModal, useProfile,
userApi를 불러 실행한다. React 훅/요소와 외부 서비스는 테스트 대역이며 운영 요청은 없다.
다음 기존 동작을 확인했다.

- 학교·교회·소개글·스쿨처치·비밀번호의 한 번 저장, 6자 이상 영구 비밀번호와 확인 불일치 처리
- 사진만/정보만/사진과 정보 함께 저장, 사진 압축·업로드 후 URL 저장
- 같은 계정의 관리자 캐시 동기화, 다른 계정 캐시는 그대로 보존
- 업로드 실패 시 DB 쓰기 없음, DB 실패 시 성공 캐시 갱신 없음, 실패 시 모달 유지
- 서버 저장 성공 후 로컬 저장소 오류가 생겨도 재저장을 유도하는 실패로 보고하지 않음

마지막 항목은 기존 useProfile에서 재현된 내부 오류로, user 캐시 쓰기를 별도 try/catch로
처리했다. DB 요청, 비밀번호 처리, 사진 업로드, 화면 입력 및 운영 절차는 바꾸지 않았다.
수정 전 파일은 `backups/profile-save-cache-20260831-233018/useProfile.js`에 보관했다.
이는 해당 소스 파일 백업이며 최신 전체 DB 백업을 뜻하지 않는다.

로컬 저장소가 차단된 경우 현재 화면의 user 상태와 성공 응답은 유지되지만, 새로고침 뒤의
캐시 복구까지 해결한 것은 아니다. 기존 해시 비밀번호 저장 방식도 이번 수정으로 안전한
Auth 저장 방식으로 전환된 것은 아니다. 신규 프로필 서버 경로는 계속 운영 미연결이다.

후속 검증 결과: 프로필 호환성·프로필 서버·로그인 컨트롤러·로그인 서버·세션 서버·회원 저장·
권한·비밀번호 코어·가입 폼의 테스트 스크립트 9개 통과.
localhost:5173의 루트와 수정 훅/프로필 모달 모듈 응답은 모두 200이었다.
`npm run build -- --outDir scratch/auth-compat-build`도 성공했다. 배포 출력 dist를 교체하지 않았다.
큰 청크, 정적/동적 import 혼용, Browserslist 데이터 및 legacy target 설정 경고는 남아 있다.
이 검증은 전체 기능의 실제 기기 E2E 검증이나 운영 Auth/Storage 통합 시험을 대신하지 않는다.
