# 인증 구조 개편 현재 로컬 상태

이 문서는 과거 설계 문서보다 우선하는 현재 구현 기록이다. 운영 DB 적용, Edge Function 배포,
Firebase 배포는 하지 않았다. `VITE_ACCOUNT_AUTH_ENABLED`가 켜지기 전 기존 화면과 경로가 유지된다.

## 유지되는 이용 방식

- 이름과 비밀번호 로그인, 동명이인 선택, 기존 화면 이동과 로컬 프로필 모양을 유지한다.
- 기존 회원은 공개 프로필 ID와 모든 활동 기록을 유지한다. 기존 비밀번호 4자리도 마이그레이션
  브리지에서 확인할 수 있으며, 일반 영구 비밀번호의 새 최소 길이는 6자리다.
- 이미 유효한 Supabase Auth 세션은 계정 매핑과 자격 증명 마이그레이션을 검증한 뒤 같은 세션으로
  계속 쓸 수 있다. 검증되지 않거나 충돌한 세션만 재인증한다.
- 회원가입은 기존 필드와 약관을 그대로 쓴다. 이름·생년월일·전화번호가 모두 일치하는 단 하나의
  미가입/게스트 기록이 있으면 같은 UUID를 서버 트랜잭션에서 승계한다. 불일치·중복이어도 가입은
  정상 완료하고 기존 기록을 보존한 채 관리자 이용자 목록에만 `연결 확인 필요`로 표시한다.
- 관리자 비밀번호 초기화는 현재 관리자 세션과 서버 저장 전화번호를 확인한 뒤 뒤 4자리를
  한 번만 쓸 수 있는 임시 값으로 만든다. Supabase Auth의 영구 비밀번호를 4자리로 만들지 않는다.
- 관리자 권한 부여/해제 화면은 유지하되, 활성화 후에는 비공개 역할 테이블과 공개 표시 역할을
  서버에서 원자적으로 바꾼다. 보호 요청은 최신 역할을 매번 확인하므로 일반 로그인 세션은 유지하면서
  권한 부여·해제 결과를 즉시 반영한다.
- 기존 이용자 관리와 학교 관리의 임시 회원 병합 화면은 유지한다. 서버가 임시 계정과 정식 계정,
  현재 관리자 권한을 다시 확인하고 포인트·활동·학교 기록을 한 트랜잭션에서 옮긴다. 중복 행은
  정식 계정 기록을 보존하고, 알 수 없는 참조나 중간 실패가 있으면 전체 병합을 롤백한다.
- 프로필, 게시물/채팅/방명록/미션, 공지/상점/배지/대여 이미지 업로드 UI는 유지한다.
  활성화 후에는 브라우저가 Storage 쓰기 경로를 선택하지 않고 검증된 서버가 고정 경로에 저장한다.

## 내부 보안 구조

- 비밀번호 확인값, 계정 매핑, 로그인 식별자, 세션 보증, 일회용 초기화 값, 가입 작업 영수증과
  canonical 역할은 `account_security` 전용 테이블에 둔다. `anon`과 `authenticated`는 읽거나 쓰지 못한다.
- Edge 서버도 service-role로 임의 SQL을 실행하지 않는다. 기능별 `NOLOGIN NOBYPASSRLS` 역할을
  트랜잭션 안에서만 `SET LOCAL ROLE`로 사용한다.
- 로그인, 후보 조회, 세션 확인, 비밀번호 변경/초기화, 프로필, 가입, 업로드, 관리자 역할 변경은
  정확한 `/account-auth` 하위 경로로 분리했다. 활성화된 새 경로가 실패할 때 공개 비밀번호/RPC로
  되돌아가지 않는다.
- 기존 SHA-256 공개 확인값은 비공개 영역으로 옮긴 뒤 keyed provider credential로 단계 전환한다.
  중간 실패는 상태로 남아 재개할 수 있고, 검증된 롤백은 Auth 비밀번호와 공개 확인값을 이전 방식으로
  복원할 수 있다. 원본 회원/활동/로그 행은 삭제하지 않는다.
- 과거 로그인·가입 병합 RPC 5개와 공개 Storage 쓰기는 최종 전환 단계에서만 철회하며 각각 별도
  롤백 SQL이 있다. `dispatch-notification`의 옛 인증 두 작업도 새 서버 준비 플래그가 켜지면 410으로 종료한다.
- `/health`는 서버와 필수 DB 구조가 함께 준비됐을 때만 성공한다. 화면 전환 전에 이 응답을 확인하며,
  장애가 나도 기존 세션을 자동 로그아웃하거나 공개 비밀번호 검증으로 우회하지 않는다.

## 검증 및 복구 지점

- 전체 Vite 운영 빌드를 `scratch/auth-secure-ui-build-20260901-1100`에 생성해 성공했다.
- 인증 단위/통합 테스트는 DB 역할·RLS, 기존 4자리 로그인, 세션 연속성, 가입과 게스트 승계,
  비밀번호 수명주기, 업로드, 역할 변경, HTTP 경계와 기존 UI 호환성을 검사한다.
- 소스 체크포인트 `backups/auth-secure-ui-20260901-1100`의 783개 파일을 해시 검증하고
  `scratch/auth-secure-ui-restore-20260901-1100`에 격리 복원해 동일성을 확인했다.
- 운영 전환 전에는 새 최종 체크포인트를 한 번 더 만들고, 기존 암호화 DB 백업의 상태와 전환 시점의
  읽기 전용 무결성 점검을 다시 확인해야 한다.

## 운영에 아직 적용하지 않은 것

현재 파일은 적용 가능한 로컬 구현과 제안 SQL이다. 운영 반영은 DB 제안 적용, 계정 부트스트랩,
자격 증명 마이그레이션, 기존 세션 보증 생성, Edge 준비 확인, UI 플래그 활성화, 약한 RPC/Storage 권한
철회, 실제 회원·관리자 회귀 확인 순서로 진행해야 한다. 어느 단계든 실패하면 활성화하지 않고 중단한다.
