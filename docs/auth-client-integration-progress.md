# 공통 로그인 연결부 진행 기록

> 후속 실제 DB 점검: 관리 화면의 기존 로그인으로 읽기 전용 조회에 성공했다.
> `auth-live-db-review-20260831.md` 참고. 아래 로컬 연결 정보 부재는 브라우저 접근 불가를 뜻하지 않는다.

현재 화면·운영 방식 유지 지시를 따른다. 기존 App, 로그인 폼, 회원 캐시, 가입 훅은 바꾸지 않았다.

## 추가한 코드

- `src/auth/loginTransport.js`: 명시적 서버 URL로 로그인 요청. HTTPS/localhost만 허용하고
  URL 내 자격/쿼리/fragment를 거절한다. 요청 제한 시간, 취소, no-store, redirect 거절,
  원문 서버 오류 숨김을 적용했다. 자동 재시도/해시 비밀번호/RPC fallback은 없다.
- `src/auth/loginController.js`: 로그인·현재 화면 재확인·현재 기기 로그아웃의 공통 연결부.
  기존 입력을 그대로 받으며 추가 입력이나 페이지 이동을 만들지 않는다.

서버 로그인 성공 → 서버 세션·회원 연결 확인 → SDK 세션 반영 → 실제 SDK 토큰 재확인의 순서다.
마지막에만 화면이 사용할 회원/Auth ID를 반환한다. 역할/해시 등 요청에 섞인 필드는 전달하지 않는다.
SDK 세션 변경은 직렬화한다. 후속 요청/로그아웃/외부 컨텍스트 변경이 오면 이전 결과를 무효화한다.
SDK 쓰기를 취소할 수 없을 때도 끝나기 전에 다음 쓰기를 실행하지 않는다.
표준 SDK 외 별도 토큰 저장소·비밀번호 저장·브라우저 캐시 인증은 추가하지 않았다.

비밀번호 거절이나 SDK 적용 전 서버 검증 실패는 기존 세션을 변경하지 않는다. 폐기할 때는
그 시도에서 발급받은 토큰만 정리하도록 별도 의존성을 받으며 공용 SDK signOut을 호출하지 않는다.
명시적 사용자 로그아웃만 scope=local을 사용한다.

**SDK 반영 중/반영 후 실패까지 기존 상태 유지가 보장되는 것은 아니다.** 이 경우 이전 토큰을
강제로 복원하거나 다른 세션을 로그아웃시키지 않고 오류를 반환한다. 실제 앱 연결에서는
기존 SessionCoordinator 및 SDK 이벤트로 상태를 다시 확인하고, 확정 전 회원 UI/보호 작업을
갱신하지 않도록 연결해야 한다. 이 연결은 아직 남아 있다.

## 검증

`node scripts/test-login-controller.mjs` 통과:
정상 로그인, 재확인 실패 시 기존 세션 유지, 회원 연결 불일치, 늦은 응답, SDK 쓰기 도중
로그아웃 순서, 외부 변경 무효화, 원문 비밀번호 공백 유지, 역할/해시 제외, URL 검증,
요청 시간 제한, 오류 원문 미노출, 요청 자동 재시도 없음.

`node scripts/test-login-service.mjs`에 새 공통 클라이언트를 추가하여 실제 loopback HTTP
`/login`·`/session` 및 PGlite의 세션 신뢰 근거 저장과 연결했다. 로그인 후 재확인 실패에도
채택된 세션이 보존되며, 명시적 로그아웃이 다른 기존 세션을 지우지 않음을 확인했다.
Auth 제공자와 SDK는 테스트 대역이다.

브라우저 간 공통 쓰기 잠금은 Web Locks를 명시적으로 주입하며 미지원 시 묵시적으로 무잠금
전환하지 않는다. 실제 브라우저 복수 탭/모바일 SDK/재시작 시험은 아직 미완료다.
UI/페이지 이동/입력 보존을 실제 운영 화면에서 검증한 것으로 해석하지 않는다.

## 후속: SDK 저장·다른 탭·인증 갱신 경합 보완

로그인 준비 코드에서 다음 실패를 먼저 테스트로 재현한 뒤 수정했다.

- `setSession`이 세션을 기록했지만 Promise가 예외로 끝날 수 있으므로, 호출을 시작한
  이후에는 발급 토큰 정리로 해당 세션을 취소하지 않는다. 이전 토큰 복원/강제 로그아웃도 하지 않는다.
- 최종 서버 검증을 기다리는 사이 다른 탭에서 SDK 계정이 바뀌면, 반환 직전 SDK를 다시 읽어
  이전 프로필 성공 결과를 거부한다. 읽기 추가뿐이며 로그인 POST/SDK 쓰기를 재시도하지 않는다.
- SessionCoordinator의 오래된 작업 캡처가 만료된 뒤 새 인증 검증이 성공해도,
  그 오래된 캡처를 다시 유효하다고 인정하지 않는다.

로그인 컨트롤러·세션 연속성·로그인 서버·세션 서버·프로필 서버 테스트가 통과했다.
SDK/외부 Auth는 모의 객체이며 실제 다중 브라우저 탭 통합 검증은 아니다.
마지막 SDK 읽기 이후의 화면 반영도 안전해야 하므로, UI에서 identity 캡처 검증 및
SDK 외부 계정 변경 이벤트 연결이 여전히 필요하다. 토큰이 같은 계정으로 정상 갱신된 경우의
연결 동작도 실제 SDK에서 검증해야 한다. 이 수정을 전체 로그인 연결 완료로 해석하지 않는다.
기존 App 로그인 경로, 운영 DB, 배포 및 사용자 로그인 상태는 이번 작업에서 바꾸지 않았다.

## 연결 전 확인과 남은 작업

- 실제 DB 구조 확인용 DATABASE_URL/SUPABASE_DB_URL/POSTGRES_URL 및 관리 API 토큰의 설정
  유무만 확인했던 시점에는 작업 프로세스와 .env/.env.local에 해당 설정이 없었다.
  이후 로그인된 Supabase 대시보드에서 읽기 전용 구조 점검을 완료했고 users의
  TRUNCATE/REFERENCES/TRIGGER 권한만 회수했다. 최신 사실은
  `auth-live-db-review-20260831.md`, `auth-users-privileges-applied-20260831.json`에 기록했다.
  이번 경합 보완 작업에서는 추가 운영 SQL을 실행하지 않았다.
- 현재 앱에는 `verifiedProfileLogin`의 legacy 해시 비밀번호 경로와 별도 로그아웃 경로가 남아 있다.
  새 모듈을 만들었다고 옛 경로가 닫힌 것은 아니다. 보호 서버·DB와 함께 전환해야 한다.
- 실제 SDK의 외부 계정 변경 이벤트 → invalidate/SessionCoordinator, 검증 후 회원 UI 갱신,
  새 세션 정리 어댑터, 동일 출처 lock 이름, 잠금 미지원 환경 대안 연결이 남아 있다.
- 현재 가입 요청 어댑터, 기존 관리자 승인과 보호 계정 상태 동기화, 모든 보호 API/RLS 검사,
  실제 Supabase 격리 시험과 전체 복구 시험이 남아 있다.

서버 준비 전 기존 화면을 새 서버에 연결하지 않았고, 운영 데이터/기존 세션/배포는 변경하지 않았다.
새 운영 조건에 대한 제안은 내부 작업 후 모아 전달한다.
