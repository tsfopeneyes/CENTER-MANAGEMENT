# 가입 인증 준비·중단 복구 진행 기록

> 최신 범위: `docs/auth-scope-current-experience.md`가 우선한다. 이 문서의 가입 근거 확인
> 계약은 실험용 준비 코드이며 기존 이용자에게 새 절차를 요구하기로 확정한 것이 아니다.
> 현재 폼을 그대로 받는 검증·저장 데이터 변환은 `registrationForm.mjs`에 별도로 구현했다.

## 현재 범위

`registrationService.mjs`, `registrationStore.mjs`, 독립 SQL 제안
`supabase/manual/proposals/auth-registration-foundation.sql`을 추가했다.
**회원 가입 전체의 실제 앱 연결은 완료되지 않았다.** 이후 회원 저장 트랜잭션과
준비 서비스의 finalizer 호출 계약을 추가했다. `docs/auth-membership-server-progress.md` 참고.
실제 앱/HTTP 경로에 연결하지 않았고 운영 계정 생성·스키마 변경·배포는 하지 않았다.

## 중복 방지와 재개

1. 신뢰된 서버 가입 확인자가 가입 근거, 제출 정보, 약관 및 보호자 요건을 확인해야 한다.
   `verifyEnrollment`는 아직 운영 어댑터가 없는 계약이다. 기본 허용 경로는 없다.
2. 브라우저가 생성하는 32바이트 난수 요청 비밀값은 원문 대신 HMAC 키로 저장한다.
   이 값은 요청 재개용이며 계정 소유 증명이 아니다. 주소/로그/분석 도구에 남겨서는 안 된다.
3. 가입 근거의 식별 키를 UNIQUE로 예약한다. 같은 요청의 제출 내용 변경, 다른 요청으로
   같은 식별자 선점은 거절한다. 식별 키 예약 전 실제 가입 근거 확인이 필수다.
   입력 전화번호만 믿으면 타인의 가입을 막는 공격이 가능하므로 그런 어댑터는 허용하지 않는다.
4. DB에서 reserved → creating 전이를 성공한 한 요청만 Supabase Admin `createUser`를 호출한다.
   네트워크 재시도나 서버 재시작으로 두 번째 계정을 만들지 않는다.
5. Auth 성공 후 응답 유실 시, 같은 처리 ID가 보호된 Auth app metadata에 기록된 계정을 조회한다.
   이메일 일치만으로는 채택하지 않으며 이름·전화번호로 기존 회원/게스트를 합치지 않는다.
6. 처음 처리와 재개 모두 사용자가 제출한 원문 비밀번호를 native Auth로 검증하고 실제 세션을 확인한다.
   비밀번호/해시/토큰을 처리 기록에 저장하지 않는다. 요청 비밀값만 알아도 비밀번호 변경은 불가능하다.
7. 마지막 DB 쓰기에서 Auth ID/이메일/서버 metadata 연결을 다시 확인하여 auth_ready로 기록한다.
   응답에는 `membership_pending`만 반환한다. Auth 토큰/ID/내부 이메일은 반환하지 않는다.
   검증에 사용한 새 세션은 정리한다. 신뢰 근거 및 회원 권한은 부여하지 않는다.

내부 이메일은 명시적으로 설정한 전용 도메인과 서버 난수 ID를 사용한다. 이메일 확인 플래그는
이 내부 라우팅 식별자를 위한 것이며 실제 사용자의 이메일·전화번호 소유 확인을 의미하지 않는다.
도메인 소유/라우팅·메일 및 Auth hook 동작 검토 없이 운영 설정하면 안 된다. 코드에 운영 도메인은 없다.

## 안전하게 중단하는 경우

- 생성 요청이 서버에 도달했는지 불명확하고 Auth 행도 없으면 `registration_pending`으로 남긴다.
  자동 재생성/예약 삭제/기존 계정 삭제를 하지 않는다. 명백한 제공자 오류도 자동 재시도하지 않는다.
- 생성 권한을 예약한 DB 응답이 유실되면 실제 Auth 호출 전이라도 동일하게 중단한다.
  정확히 한 번 성공을 보장하는 방식이 아니라, 불확실할 때 두 번 만들지 않는 보수적 방식이다.
- 유효기간은 최초 예약 기준이며 재시도로 연장하지 않는다. 만료되어도 식별 키 예약을 자동 해제하지 않는다.
  늦은 Auth 생성 완료와 충돌할 수 있으므로 운영자 확인 후 별도 복구가 필요하다.
- 자격 증명/회원 연결이 없는 Auth 사용자는 모든 보호 API/RLS에서 접근이 거절되어야 한다.
  이 조건과 기존 취약 발급 경로 종료 전에는 readiness를 활성화할 수 없다.

## 검증

`node scripts/test-registration-service.mjs` 통과. 독립 PGlite에서 실제 SQL/권한을 사용했다.

- 정상 인증 준비, 같은 요청 재개, 비밀번호 오입력, 제출 정보 변경, 식별 키 충돌
- Auth 생성 성공 후 응답 유실, auth_ready 쓰기 성공 후 응답 유실, claim 응답 유실
- 동일 예약의 동시 20개 claim 중 생성 권한 1개만 허용
- 이메일만 같은 타 계정 채택 거절, 잘못된 세션 ID 소유 거절, 최종 기록 전 metadata 변경 거절
- 만료/취소/미준비 서버/가입 근거·정책·시도 제한 거절, 검증 세션 정리
- 기존 공개 회원 원본 보존, worker의 회원/Auth 수정·처리 기록 삭제 거절,
  anon/authenticated 비공개 기록 접근 거절, 기록 내 원문 비밀번호/요청 비밀값/전화번호 없음

Auth, 가입 확인자, 비밀번호 정책, 제한 제공자는 테스트 대역이다. 이 테스트는 실제 Supabase
Admin API 또는 운영 다중 연결 부하 테스트가 아니다. 이번에 운영 회원은 생성하지 않았다.

## 다음 구현 항목

- 기존 공개 회원 스키마의 실제 제약/트리거를 확인하고, 회원 저장·Auth 연결·로그인 식별자 저장·
  처리 완료를 하나의 DB 트랜잭션으로 구현한다. 기본 역할은 일반 이용자로 고정하고 미성년자
  보호자 승인 상태를 유지한다. 해당 finalizer 및 격리 권한 제안은 추가했고, 실제 스키마
  확인과 기존 가입 경로 통합은 아직 남아 있다.
- 가입 근거 확인 및 모든 가입 입력/약관/보호자 검증 어댑터. 전화번호를 공동 사용하거나 변경한
  이용자의 정책도 필요하다. 기존 회원 연결·게스트 전환은 별도 소유 확인/관리자 절차다.
- 실제 SDK/HTTP 오류·시간 제한, 입력 크기 제한, 신뢰 ingress, 브라우저 재개 UX,
  미완료 작업 관찰·관리자 복구 도구, 기존 인증 경로 정리와 전역 RLS 검사.
- 최신 백업/전체 서비스 복구 리허설 및 실제 격리 Supabase 시험. 운영 전환 승인은 별도다.
