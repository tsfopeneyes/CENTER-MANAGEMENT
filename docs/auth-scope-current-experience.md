# 인증 개편 범위 — 현재 경험 유지

이 문서는 사용자의 최신 지시를 반영하며, 이전 계획/진행 문서에 포함된 운영 변경 가정보다 우선한다.

## 최신 정정 — 회원 승인 운영을 가정하지 않음

사용자는 회원 승인 절차가 없었다고 정정했다. 코드에 만 14세 미만 pending 상태와
보호자 확인 후 승인 안내가 있다는 사실만으로 실제 운영 절차라고 단정하지 않는다.
전원 승인제나 새 가입 대기 절차를 도입하지 않는다. 기존 가입 화면과 처리는 이번 정정에서
변경하지 않는다. 잘못된 가정으로 만든 membershipApprovalService/클라이언트/SQL/테스트와
accountAuthService의 승인 경로 등록은 모두 제거했다.
준비용 가입 코어의 pending→승인 요구도 검증된 운영 요구로 간주하지 않으며,
기존 가입 동작을 바꾸는 방식으로 연결해서는 안 된다.

가입 준비 코어는 기존 public.users의 만 14세 미만 status/보호자 필드는 그대로 만들지만,
그 값을 새 인증 계정의 차단 상태로 복제하지 않는다. 보호 계정은 active, 로그인 identifier는
enabled로 생성하며 가입 결과는 다른 이용자와 동일한 registered다. 이는 현재 화면의 상태 필드를
삭제하거나 기존 관리자 화면을 변경하는 작업이 아니라, 새 인증 구조에 별도 승인 관문을 만들지
않기 위한 내부 호환 처리다.

## DB 구조 변경 허용 — 최신 지시

사용자가 “가장 안정적인 형태가 있다면 DB를 변경해도 된다”고 명시했다.
인증 안정성·안전에 필요한 DB 구조/권한 변경을 허용한 것으로 반영한다. 이전 AGENTS의
구조 변경 금지를 이번 인증 작업의 절대 제약으로 적용하지 않는다. 원본 데이터·로그 보존,
현재 이용 경험 유지, 별도 운영 변경안의 사후 제안, Firebase 배포 제한은 계속 유지한다.
실제 구조 점검·최신 백업·복구 검증·기존 호출 경로 호환성을 충족한 변경부터 단계적으로 진행한다.

## 확정된 작업 기준

- 기존 로그인·가입 화면, 입력 항목과 청소년/졸업생 구분을 유지한다. 만 14세 미만
  보호자 관련 코드가 실제로 어떻게 사용되는지는 운영 사실과 구분하며 새 절차를 추가하지 않는다.
- 인증 검증과 회원 연결, 권한 판단, 실패·동시 요청 처리를 서버 내부에서 일관되게 만든다.
- 이용자 경험/운영 방식 변경안은 나머지 작업 후 모아서 제안한다. 그 전에 적용하거나
  새 승인 절차를 기본 요구사항으로 구현하지 않는다.
- DB 구조 변경은 위 범위에서 허용되었다. 검증되지 않은 계정 변경/파괴적 전환이나 배포는 하지 않는다.
  현재 추가한 서버 모듈은 실제 앱에 미연결이다.

## 이번에 수정한 가정

- 임의로 추가한 새 비밀번호 12자 최소 조건을 준비용 서버 코어에서 제거했다.
  사용자 결정에 따라 영구 비밀번호는 6자 이상 입력받는다. 실제 Auth의 정책 검사도 별도로 수행하며,
  호환되지 않는다고 정책을 낮추거나 해시/접두사로 우회하지 않는다.
- `registrationForm.mjs`는 기존 formData/agreements를 받아 서버에서 필드를 검증하고
  비밀번호 없는 회원 저장 데이터를 만든다. 새 인증번호, 본인 확인 질문, 전원 관리자 승인을 요구하지 않는다.
- 기존 그룹은 청소년/졸업생만 받고 role은 user로 고정한다. status는 서버가 생년월일로
  기존 under14 규칙을 계산한다. 클라이언트 role/status/ID/preferences 주입을 거부한다.
- 가입 제출 시 한국 날짜를 기준으로 생일을 계산하고 존재하지 않는 날짜를 거부한다.
  비밀번호 확인 불일치, 약관 미동의 등은 서버에서도 확인한다. 저장/가입 승인 기능은 아니다.

## 기존 준비 코드의 격리

이전 `registrationService`의 `verifyEnrollment`, `enrollmentId`, identity 예약은 검증된 가입
근거를 가정한 실험용 계약이다. **현재 가입 방식의 필수 절차로 채택한 것이 아니다.**
기존 폼 검증 결과만으로 `verifyEnrollment.allowed=true`를 만들어 우회해서는 안 된다.
현재 가입 방식에 맞는 내부 요청/회원 저장 경로가 완성되기 전에는 이 서비스에 연결하지 않는다.

`credentialService`는 별도 MFA를 추가하지 않고 기존 관리자 확인을 사용한다. 초기화 네 자리는 private digest로만
보관되는 일회용 변경 자격이다. 운영 hasher·검증 어댑터·복구 도구가 없어 현재 관리자 화면에는 연결하지 않는다.

## 작업 후 함께 제안할 항목 — 현재 미적용

- 전화번호 뒤 4자리 초기화는 native Auth와 분리한 일회용 변경 자격으로 유지한다.
- 추가 본인 확인 또는 비밀번호 변경 요구가 불가피한 대상과 화면상 영향
- 기존 게스트 자동 연결을 안전하게 유지할 수 없는 경우의 처리 대안
- 관리자 MFA, 임시 비밀번호 만료·변경 강제, 추가 가입 확인의 필요 여부

지금은 위 항목의 동의를 요청하지 않는다. 내부 작업과 검증이 끝나면 필요 이유, 유지 가능한
부분, 대안 및 이용자/관리자 영향을 비교해서 제안한다. 서로 양립하지 않는 요구를 모두
구현 완료했다고 표현하지 않는다.

## 검증 및 다음 내부 작업

프로필 일반 정보·스쿨처치 설정의 서버 수정 경로를 격리 구현했다.
현재 입력에 없던 글자 수 제한은 제거했으며 사진·비밀번호 통합 저장은 기존 경로를
유지한다. 부분 서비스로 화면을 교체하지 않는다. 검증과 남은 범위는
`auth-profile-server-progress.md`에 기록했다.

`node scripts/test-registration-form.mjs`로 기존 그룹/6자 이상 영구 비밀번호/학교 정규화/보호자 규칙/
한국 생일 경계/역할 주입 거부/비밀번호 없는 profile 출력을 확인한다.
로그인·가입 인증 준비·비밀번호 변경 기존 테스트도 계속 유지한다.

회원 저장 트랜잭션은 격리 구현했다(`auth-membership-server-progress.md`).
회원 데이터의 실제 트리거/제약 확인, 공통 로그인 연결, 보호 데이터의
권한 검사는 아직 남아 있다. 특히 기존 `isAdminOrStaff`의 이름 기반 판정은 서버 권한 검증에
재사용하지 않는다. 새 서버 권한은 보호된 역할 정보로 판단해야 한다.
