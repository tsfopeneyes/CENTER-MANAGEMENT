# 로그인 보안 전환 — 로컬 구현, 운영 미적용

2026-08-31. 배포와 운영 DB 변경은 하지 않았다. 기존 캘린더 작업은 유지했다.
이 문서는 배포 승인이나 운영 보안 문제가 이미 해결되었다는 의미가 아니다.

후속으로 운영 전환 승인을 받았으나, 사전 점검에서 미연결 인증 계정 12개·복구 필요 회원 12명과
확인되지 않은 백업이 발견되어 실행 전에 중단했다. 현재 상태와 재개 조건은
[운영 사전 점검](./account-auth-operational-preflight.md)에 기록했다.

## 현재 준비한 변경

- 이름·비밀번호 로그인 화면과 동명이인 선택을 유지한다.
- `account-auth` 서버만 비밀번호를 검증한다. 후보 목록에는 이름·학교·회원 유형·프로필 ID만 반환한다.
- 기존 비밀번호 확인값은 서버 전용 영역으로 보존하고 공개 프로필의 값은 비운다.
  기존 회원 ID, 신청, 포인트, 원본 출입 기록은 변경하지 않는다.
- 기존 SHA-256 확인값을 비밀번호로 그대로 제출하는 요청은 거부한다. 최초 정상 로그인 후
  서버 비밀값으로 분리한 Supabase Auth 자격 증명으로 전환한다. 서버 비밀값은 브라우저로 전송하지 않는다.
- 새 세션은 서버 전용 세션 목록에 연결한다. 오래된 Auth 세션이나 브라우저 프로필을 꾸민 것만으로
  새 계정 관리·프로필 수정·캘린더 관리자 권한을 얻을 수 없다.
- 비밀번호 변경은 로그인한 본인만 가능하다. 관리자 초기화는 서버에서 확인한 관리자에게만 허용하고,
  사용자 요청에 따라 서버에 등록된 휴대폰 번호 뒤 4자리로 재설정한다. 전체 번호를 우선 사용하고
  전체 번호가 없는 기존 회원만 저장된 `phone_back4`를 사용한다. 잘못된 번호·탈퇴 회원은 거부한다.
  브라우저가 보낸 번호는 사용하지 않으며 초기화 응답에도 비밀번호를 포함하지 않는다.
  관리자 계정 복구는 서버 운영자가 담당한다.
- 비밀번호 변경 시 이전 세션의 세대 값을 폐기한다. 권한 변경도 기존 세션을 폐기한다.
- DB에 공유되는 횟수 제한과 조건부 갱신을 사용한다. 인증 장애 때 과거의 약한 검증으로 되돌아가지 않는다.
- 예전 `ensure-auth-link`, 생년월일·전화번호 끝자리 기반 `reset-student-password`는 종료한다.
- 관리자 화면에서 비밀번호 확인값으로 실제 비밀번호를 추측하던 코드를 제거한다.
- 회원가입·비밀번호 변경은 공개 `users.password`에 쓰지 않는다. 게스트의 공통 비밀번호 `0000`도 없앤다.
- 커피챗 서버의 계정 확인도 검증된 새 세션을 사용한다. 멘션 검색은 인증 RPC 대신 필요한 표시 필드만 조회한다.

## 이용자가 체감하는 차이

- 평소 이름·비밀번호 로그인 방식은 같다. 전환 후 다시 로그인해야 한다.
- 비밀번호를 잊었을 때는 센터 관리자의 본인 확인이 필요하다.
- 관리자 초기화 후 등록된 휴대폰 번호 뒤 4자리를 전용 변경 화면에 한 번 입력하고 새 영구 비밀번호를 정한다.
  네 자리는 일반 로그인이나 Supabase Auth 비밀번호로 쓰지 않으며 변경이 끝나면 즉시 무효가 된다.
- 기존 게스트/미가입 기록을 정식 회원 계정에 연결하는 자동 병합은 중단한다.
  공개된 전화번호나 프로필 ID만으로 과거 기록을 가져오면 본인 확인이 되지 않기 때문이다.
  이 전환은 서버 운영자의 검증된 계정 연결 절차로 처리해야 한다. 일반 신규 가입은 유지한다.
- 관리자 화면의 기존 수동 병합도 임시 중지한다. 서버 거절 뒤 브라우저가 기록을 직접 옮기거나
  삭제하는 우회 코드를 제거했고, 안전한 서버 처리 절차가 준비될 때까지 연결 확인 안내만 제공한다.
- 비밀번호 확인값이 없는 기존 Auth 전용 계정, 관리자 복구, 서버 갱신 중 실패한 계정은 운영자가 확인한다.
  이들을 임의로 재가입시키거나 기존 기록을 지우면 안 된다.

## 로컬 화면 오류와 복구

아직 없는 새 인증 서버에 세션 확인 화면을 먼저 연결해 `로그인 상태를 확인하지 못했습니다`가 표시되었다.
`VerifiedAccount`의 개발용 미리보기와 운영용 세션 확인을 분리해 기존 로컬 캘린더 탐색을 복구했다.

- 기본 `npm run dev`: 기존에 저장된 로그인 상태로 로컬 화면을 살펴볼 수 있다.
- `VITE_ACCOUNT_AUTH_LOCAL_ENABLED=true`: 독립 인증 서버를 준비한 뒤 새 세션 확인까지 검증한다.
- 운영 빌드: 위 개발 옵션과 관계없이 반드시 새 서버 세션을 확인한다.
- 로컬에서 새 로그인·회원가입·비밀번호 변경을 실제로 저장하려면 새 서버와 DB 전환이 필요하다.
  화면을 볼 수 있다는 이유로 운영 인증 보호까지 적용되었다고 해석하면 안 된다.
- `/scratch/account-auth-preview.html`: 외부 요청과 저장소를 격리한 가상 UI 검사. 실제 회원·DB 저장 없음.

## 운영 반영 전 필수 확인

**현재 화면은 새 인증 서버가 없는 운영 환경에서 로그인할 수 없다.** 서버·DB·화면을 함께 전환해야 한다.
자동 마이그레이션 폴더가 아닌 `supabase/manual/account-auth-cutover.sql`에 수동 적용 파일을 두었다.

### 2026-08-31 추가 확인 및 배포 방지 장치

- 설정된 운영 `account-auth`에 인증 정보 없는 GET 요청을 보냈고 HTTP 404를 확인했다.
  회원·비밀번호·세션을 조회하거나 변경하지 않았다. 새 인증 서버가 준비됐다고 볼 수 없다.
- `supabase/config.toml`에 누락된 `[functions.account-auth]`를 추가했다.
  로그인 전 요청을 받도록 게이트웨이 JWT 검사를 끄되, 보호 작업의 실제 Auth 사용자/서버 세션 검증은 유지한다.
  이는 로컬 설정이며 운영 함수가 배포되었다는 뜻이 아니다.
- `GET /functions/v1/account-auth/health`를 추가했다. 서버 활성화·비밀값 설정·전환 대기 종료,
  필수 인증 테이블 존재·미완료 회전을 읽기 전용으로 확인한다. 응답은 서비스명/프로토콜/준비 여부뿐이다.
  이 검사는 실제 계정 로그인, 전체 권한 감사, 백업, 알림 서버 전환 검증을 대신하지 않는다.
- `firebase.json`의 Hosting 사전 단계에서 새 빌드, 번들의 인증 경로 검사, 운영 준비 상태 검사를 실행한다.
  404/401/503, 미완료 전환, 통신 실패 또는 잘못된 응답이면 배포를 중단한다. 개발용 인증 예외를 운영에 넣거나
  이전의 약한 인증으로 돌아가는 우회 옵션은 추가하지 않았다.
- `node scripts/check-account-auth-readiness.mjs`는 운영 준비 상태만 GET으로 점검하며 배포·계정 변경을 하지 않는다.
  현재는 HTTP 404로 **실패하는 것이 정상**이다. 검사만 통과시키려고 설정을 강제로 켜면 안 된다.
- `node scripts/test-account-auth-readiness.mjs` 및 기존 인증/전환/독립 DB/번들 테스트를 통과했다.
  실제 Edge 런타임 배포와 운영 계정 로그인 검증은 아직 하지 않았다.
- 근본 해결에는 아래 유지보수 절차에 대한 별도 승인이 필요하다. 회원 ID·신청·포인트·원본 로그는 보존하되,
  인증 저장 구조·접근 권한·Auth 자격 증명·세션은 바뀌므로 단순 화면 수정으로 처리하지 않는다.

설정 근거: [Supabase 함수 설정](https://supabase.com/docs/guides/functions/function-configuration),
[Firebase 사전 배포 단계](https://firebase.google.com/docs/cli#predeploy_and_postdeploy_hooks).

### 승인 후 전환 순서

1. 운영 반영에 대한 별도 승인을 받고 중단 가능 시간을 잡는다. 기존 최대 JWT 유효시간만큼의
   전환 대기 시간이 필요하므로 무중단 적용으로 안내하지 않는다.
2. 비밀값이 없는 구조/권한 점검 결과로 실제 `users` 컬럼·트리거·뷰·RPC 목록을 검토한다.
   `scratch/auth-security-audit.sql`은 점검 쿼리이며 이번 작업에서는 운영 실행하지 않았다.
   임의 SQL 실행 RPC, `auth.users`를 읽거나 쓰는 RPC, 원본 비밀번호의 복제본/뷰/백업,
   Realtime publication의 이전 행 노출이 없는지 확인한다. 알려진 두 RPC 철회만으로 이 검토를 대신하지 않는다.
3. 가입·계정 변경 트래픽을 중지하고 Auth의 공개 직접 가입을 끈다. 알려지지 않은 Auth ID나 잘못된 연결이
   있으면 전환 SQL/회전 도구는 중단한다. 삭제하거나 임의로 연결하지 말고 소유권을 확인한다.
4. 계정/인증 데이터의 암호화된 서버 백업을 준비한다. 검토한 수동 SQL을 적용한다.
   서비스 전용 테이블은 RLS와 권한 철회를 함께 사용하며, 원본 비밀번호 보관 영역은 API에 공개하지 않는다.
5. `account-auth`와 변경된 `dispatch-notification`을 함께 배포한다. 비로그인 진입을 지원하도록
   `account-auth`의 게이트웨이 JWT 검사 설정을 조정하되, 보호 작업은 함수 내부에서 실제 JWT와
   서버 세션을 검증한다. `ACCOUNT_AUTH_ENABLED`는 검증 완료 전 false로 둔다.
6. 별도 생성한 충분히 긴 `ACCOUNT_AUTH_PEPPER`를 서버 비밀 설정에만 넣고 안전하게 백업한다.
   `VITE_` 변수, 소스 코드, 콘솔, 브라우저에 넣지 않는다. 임의 교체하면 기존 로그인 파생값이 달라진다.
7. 회전 도구를 먼저 기본 읽기 전용 모드로 실행한다. 적용 승인이 있는 경우에만 `--apply`를 사용한다.
   `ACCOUNT_AUTH_LEGACY_JWT_LIFETIME_SECONDS`에는 실제로 과거 발급된 토큰의 최대 수명을 넣는다.
   도구는 기존 Auth 비밀번호를 무작위 값으로 바꾸고 로그인을 잠근 뒤, 기존 토큰 만료 대기 시각을 저장한다.
   계정/비밀번호/토큰은 출력하지 않는다. 작업 중 끊기면 활성화하지 않고 같은 전환 작업을 재개한다.
8. 만료 대기가 끝나면 서버 활성화 및 Firebase 화면 배포를 함께 진행한다. 최초 정상 비밀번호 검증을
   통과한 계정만 서버가 새 인증 방식으로 전환하고 잠금을 해제한다. 이전 세션은 허용 목록에 없으므로 거부한다.
9. 실제 승인된 테스트 계정으로 기존 회원/관리자 로그인, 동명이인, 신규 가입, 비밀번호 변경·초기화,
   QR 출입, 프로그램 신청, 당직 저장을 확인한다. 익명 조회에서 비밀번호가 없고 회원이 다른 회원의
   비밀번호·역할·Auth 연결을 변경할 수 없는지도 확인한다.

## 실패와 복구

- 계정 변경은 여러 서비스에 걸친 작업이므로 원자적 DB 트랜잭션으로 가장하지 않는다.
  Auth 갱신 또는 최종 저장이 실패하면 `lock_id`를 남기고 추가 로그인을 거부한다.
  원본 비밀번호·기록을 지우는 보상 작업이나 시간만 지나면 잠금을 푸는 처리는 하지 않는다.
- 운영자는 해당 요청이 더 이상 실행 중이 아님을 확인하고 Auth ID/이메일·현재 비밀번호 변경 상태를
  대조해 확정하거나, 본인 확인 후 새 비밀번호를 설정해 복구한다. 잠금만 무조건 해제하면 안 된다.
- 신규 가입 두 번째 저장이 실패하면 생성된 Auth/프로필을 보존해 연결 상태를 정리한다.
  사용자의 재시도 때문에 중복 회원이 생성되지 않는지 실제 스키마의 전화번호 고유 제약도 확인한다.
- 공개 비밀번호 값을 되살리거나 약한 복구 API를 다시 켜는 롤백은 사용하지 않는다.
  장애 시 안내 화면을 유지하고 서버에서 앞으로 진행하는 방식으로 복구한다.
- 인증 회전 도구는 **전환 중에만** 재개한다. 서비스 활성화 뒤 다시 돌리는 일상 관리 도구가 아니다.

  시도 제한, 가입 입력, 캐시 정리를 확인한다.
- `node scripts/test-account-auth-database.mjs`: 독립 PostgreSQL(PGlite)에 전환 SQL을 실행해
  원본 보존, 공개 확인값 제거, 비밀 테이블 권한, 기존 definer RPC를 통한 쓰기 차단,
  본인 프로필만 수정, 게스트 출입 정보 수정, 관리자 세션과 폐기를 확인한다.
- `node scripts/test-account-auth-cutover.mjs`: 운영 전환 도구가 기본적으로 저장하지 않는지,
  미확인 Auth 계정·이미 활성화된 환경을 거부하는지, 실패 시 비활성 상태를 유지하고
  이전 토큰 만료 대기를 설정하는지 가상 서비스로 확인한다.
- `node scripts/check-account-auth-bundle.mjs`: 운영 빌드에 개발용 인증 예외와 이전 인증 경로가 없고
  새 서버 인증 확인이 포함되어 있는지 확인한다.
- 로컬 브라우저에서 기존 로그인 양식, 동명이인 선택, 학생 화면 이동, 복구 안내를 가상 자료로 확인한다.
- 전체 Vite 빌드를 확인한다. 기존 번들 크기와 Browserslist 경고는 이 변경의 범위 밖이다.
- 실제 Supabase Edge/Deno 배포·실계정·운영 데이터 전환 검증은 하지 않았다.
  이 로컬 검증을 운영 환경 전체의 보안 완료로 표현하지 않는다.
- 과거 유출 여부나 계정 도용 여부를 조사한 것은 아니다. 이미 알려진 비밀번호를 계속 쓸 수 있게 하는
  호환 전환이므로 노출이 확인된 계정은 별도로 비밀번호를 바꿔야 한다.
- 공개 회원 개인정보/게스트 기록과 다른 기능의 광범위한 접근 정책은 별도 과제다.
  이 작업은 모든 테이블의 개인정보 보호나 권한 정책을 전면 개편하지 않는다.

권한 설계는 [Supabase API 보안 문서](https://supabase.com/docs/guides/api/securing-your-api),
토큰 만료와 전환 고려사항은 [Supabase 세션 문서](https://supabase.com/docs/guides/auth/sessions)를 참고했다.
