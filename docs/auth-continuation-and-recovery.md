# 전체 인증 전환과 코드 복구 확인

**후속 정정:** 사용자가 회원 승인 운영이 없었다고 정정했다. 코드만 보고 실제 운영
절차라고 잘못 판단해 만들었던 승인 코어/SQL/클라이언트/테스트는 모두 제거했다.
기존 가입 UI나 운영 DB를 변경하거나 새 승인제를 적용한 것은 아니다.

사용자 지시: 기능·운영 변화 없이 내부 보안과 안정성만 개선한다. 자잘한 수정마다 작업을
끝내지 않고 전체 단계로 진행한다. 운영 적용은 복구 및 호환성 검증을 충족해야 한다.

## 코드 복구 — 실제 확인한 범위

- `backups/auth-baseline-20260831-213543`: manifest의 654개 파일 크기와 SHA-256 모두 일치.
- 이를 `scratch/auth-baseline-restore-20260831-2350`에 실제 복사하고 654개 전부 다시 검증했다.
  현재 작업 폴더에 덮어쓰거나 파일을 삭제하지 않았다.
- 기준점에 있던 src 328개를 현재와 비교했다. 누락은 없고 변경은 SessionCoordinator,
  RecruitmentInterestButton의 JSX 오류 수정, useProfile의 캐시 오류 처리 3개였다.
  기준점 이후 새로 추가된 파일은 이 비교 대상에 포함되지 않는다.
- `backups/auth-continuation-20260831-2350`: 이번 작업 시작 전 현재 소스·설정·잠금 파일·공개 자산
  698개를 추가 보관하고 해시 검증했다. 이후 변경은 별도 새 체크포인트로 보존한다.
- 최초 인증 작업 이전 전체 상태의 일괄 복원을 증명한 것은 아니다. 21:35 기준점은 이미
  일부 인증 준비 코드가 포함된 중간 시점이고 당시 JSX 오류도 있으므로 정상 빌드 기준과 구분한다.
- 소스 백업에는 .env, DB, Supabase Storage 원본 파일, 서버 비밀값, 클라우드 설정,
  git 객체나 node_modules가 없다. 이 문서는 소스 복구를 전체 서비스 복구로 표현하지 않는다.

도구: `node scripts/source-checkpoint.mjs verify <백업경로>` 및
`rehearse <백업경로> scratch/<새복원폴더>`.
create/rehearse는 기존 폴더를 재사용하지 않는다. 해시 불일치·경로 이탈·링크는 중단한다.
운영 소스에 덮어쓰는 명령은 제공하지 않았다. 실제 원복 때는 기준점을 고르고 현재 상태를
먼저 보관한 뒤 변경 파일과 이후의 다른 작업을 대조해 적용해야 한다.

## 제거된 승인 가정

레거시 소스의 만 14세 미만 pending 문구를 실제 운영 절차로 단정하지 않는다.
준비 가입 코어의 pending/guardian_pending 가정도 현재 전환에 연결하지 않는다.
새 승인 API, 관리자 버튼, 추가 확인 절차 또는 가입 대기 상태를 만들지 않는다.

## 전체 전환의 핵심 호환성 충돌 — 실제 근거

Supabase 운영 관리 화면의 Email 설정을 읽기 전용으로 확인했다. 최소 길이 안내는 6자이며,
PASSWORD_MIN_LENGTH 입력 값은 빈 값이었다. 빈 값을 운영의 명시적 숫자 설정으로 해석하지 않는다.
설정을 저장하거나 실제 회원 비밀번호를 시험하지 않았다.

공식 Auth 소스는 Password.MinLength가 defaultMinPasswordLength보다 작으면 최소값으로
올린다. 관리 화면의 최소 6자 안내와 일치한다. 현재 4자리 신규 영구 비밀번호를 그대로
native Auth 원문 비밀번호로 전달하는 것은 지원되는 전환 경로가 아니다. 초기화용 네 자리는
2026-09-01 설계에서 native Auth와 분리한 일회용 변경 자격으로 해결했다.

- 공식 근거: https://github.com/supabase/auth/blob/master/internal/conf/configuration.go
- 운영 화면: https://supabase.com/dashboard/project/erecqalsxoxrufggvmcc/auth/providers
- 일반 정책: https://supabase.com/docs/guides/auth/password-security

기존 방식은 SHA-256 문자열을 Auth 비밀번호로 보내 길이 조건을 충족하던 구조다.
공개 해시를 다시 이용하거나 접두사로 길이를 늘려 새 표준 구조가 완료됐다고 주장하지 않는다.
2026-09-01 사용자 결정으로 새 가입과 영구 비밀번호 변경은 6자 이상으로 맞췄다. 기존 회원의 현재
비밀번호는 준비 단계에서 바꾸지 않는다. 관리자 초기화 네 자리는 native Auth에 넣지 않고 전용 변경
요청 한 번에만 쓰므로 제공자 최소 길이를 우회하지 않는다.

## 남은 단계

현재 소스 복구는 확인했고, 가입·세션·프로필의 격리된 서버 경로는 준비 중이다.
기존 계정의 신뢰 가능한 연결, 로그인·사진·일반 비밀번호 저장·
관리 작업의 전체 연결, 53개 public 테이블/Storage/기존 RPC 권한 정리, 실제 기기 통합 시험,
최신 전체 백업·복원 시험은 완료되지 않았다. 테스트가 통과한 준비 코드만으로 운영 전환하지 않는다.

## 이번 통합 검증 결과

소스 체크포인트, 7개 SQL 제안 동시 설치,
로그인 컨트롤러/서버, 세션 코디네이터/서버, 권한, 자격 변경 코어,
가입 폼/가입 준비/회원 저장, 프로필 서버/기존 프로필 저장 코드의 총 15개 스크립트를 확인했다.
부하가 큰 병렬 실행에서 로그인 서버의 25ms 테스트가 의도한 Auth 응답 단계 이전에
만료되는 경합을 발견했다. 실제 cleanup 결함으로 단정하지 않고, 해당 테스트의 타이머를
명시적 Auth 응답 경계에서 발화하도록 바꿔 반복 통과를 확인했다. 운영 타이머 기본값은 유지했다.

전체 앱을 `scratch/auth-continuation-build`로 빌드했다(성공, 큰 청크/혼용 import/기존 브라우저
데이터 경고 유지). localhost:5173와 신규 클라이언트 모듈 응답도 200이었다.
배포 dist를 교체하지 않았고 Firebase/Supabase 배포, 추가 운영 SQL, 계정 변경은 없었다.
SDK/외부 Auth/Storage는 테스트 대역이며 실제 운영 계정 및 다중 기기 검증 완료는 아니다.
