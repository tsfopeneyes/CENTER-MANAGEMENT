## 최신 운영 반영: 관심 확인·종 알림·관리자 하트 집계

사용자의 `응 배포해줘` 승인으로 아래 로컬 변경을 운영 반영했다. 아래의 ‘로컬/미적용’ 표시는 구현 당시 이력이다.

- 10500 관리자 집계 뷰 SQL 파일 하나만 적용했다. 기존 테이블·정책·회원·원본 로그 변경 및 전체 migration push 없음.
- 운영 읽기 전용 트랜잭션에서 Jin의 서버 등록 관리자 인증으로 집계 건수/합계가 원본과 일치함을 검증했다. 일반 계정 결과 0행, 익명 SELECT 권한 없음도 확인했고 ROLLBACK했다. 적용 전 관심 등록 1건, 즉시 발송 대상 0건이었다.
- send-recruitment-alerts 함수만 갱신했다. 기존 예약/비밀 설정을 바꾸지 않았고, 별도 수동·테스트 알림은 보내지 않았다. 기존 예약 발송은 계속 정상 조건에 따라 동작한다.
- Firebase Hosting 배포 완료. 하트 확인 팝업, 즉시 관심 확인 종 알림, 모집 시작 종 알림 조회, 관리자 조회수 옆 관심 인원 표시가 포함됐다. 새 인증 전환 의존성은 없다.

## 사용 흐름

### Jin 단일 기기 테스트

후속 대화에서 사용자가 로그인 성공을 확인했고, 테스트 재발송을 승인했다.
Jin의 연결 Auth와 활성 관심 등록 1건 및 다른 계정과 토큰이 공유되지 않음을 재확인했다.
전용 임시 함수로 해당 기기에만 재시도 없이 1회 발송: HTTP 200, FCM 200,
accepted=true, recipients=1. 원격 임시 함수와 로컬 발송 소스는 삭제했다.
기존 관심 등록/정규 발송 대기열은 수정하지 않았으며 실제 기기 수신은 사용자 확인 대기다.

사용자가 다른 이용자에게 절대 발송하지 말 것을 명시하고 본인 수신 테스트를 요청했다.
Jin의 정확한 관심 등록·Auth 연결을 확인하고 다른 계정과 같은 토큰을 공유하지 않는지 서버에서 확인했다.
전용 임시 함수에서 고정된 관심 ID/소유자/동의 revision/프로필을 모두 일치 검사한 뒤 단일 토큰으로 1회 전송했다.
Firebase HTTP 200, accepted=true, recipients=1. 자동 재시도나 전체 발송 함수 호출은 하지 않았다.
임시 원격 함수 및 로컬 발송 소스는 테스트 후 삭제했다. 정규 관심 등록은 enabled=true, pending, attempts=0으로 유지됐다.
기기 표시/실수신은 사용자 확인 대기이며, Firebase 접수를 실제 수신으로 단정하지 않는다.

- 모집 예정 카드의 일정 버튼 옆 하트 → 브라우저 알림 허용 → 본인 관심 등록 저장 성공 후 `모집 시작 시 알림이 와요!`.
- 채워진 하트를 다시 누르면 취소. 카드 본문/일정 버튼은 여전히 상세 화면을 열지 않는다.
- 권한 거절, 인증 부재, 저장 실패 시 성공 안내를 표시하지 않는다. 다른 카드의 같은 프로그램도 신청 상태를 갱신한다.
- 프로그램당 계정별 한 건, 마지막으로 신청한 기기의 토큰을 저장한다. 모든 기기에 동시 발송하는 기능은 아니다. 공유 기기에서는 알림이 기기 사용자에게 보일 수 있다.

## 현재 로그인과 호환

현재 로그인 코드의 Supabase Auth 세션을 사용한다. 기존 로그인/회원 데이터를 수정하지 않는다.
브라우저에 저장된 회원 프로필만 있고 인증 세션이 없다면 재로그인이 필요하다.
관심 등록은 `auth.uid()` 소유자와 연결되며 공개 users 테이블의 role/auth_user_id/fcm_token을 신뢰하지 않는다.
로그인 UI/비밀번호 입력 방식이 바뀌어도 같은 Auth ID가 유지되면 재구현할 필요 없다.
Auth ID를 재발급하는 전환에는 기존 관심 등록의 소유자 연결 계획이 필요하다. 이 기능이 기존 로그인 전체의 보안 문제를 해결하는 것은 아니다.

## 운영 반영 전 필수 확인

1. 별도 승인 후 10400 신규 테이블/정책/서비스 전용 뷰 SQL을 검토·적용한다. 기존 notices 모집 필드(10000)가 선행되어야 한다. 기존 데이터/로그/정책 삭제 없음.
2. `send-recruitment-alerts` 함수를 별도 배포한다. 기존 send-push를 호출하거나 전체 대상 발송 경로를 사용하지 않는다.
3. 함수 비밀 설정: `FIREBASE_SERVICE_ACCOUNT`, 32자 이상의 무작위 `RECRUITMENT_ALERTS_CRON_SECRET`, 끝 슬래시 없는 HTTPS `RECRUITMENT_APP_ORIGIN`. 환경의 SUPABASE_URL/SUPABASE_SERVICE_ROLE_KEY도 필요하다. 비밀값을 브라우저나 저장소에 넣지 않는다.
4. 먼저 ENABLED 미설정(기본 중지) 상태에서 일반 사용자 요청 401, 비밀 누락 401, 정상 비밀+중지 503을 확인한다.
5. 알림 대상 테스트 계정의 로그인/권한/기기 토큰으로 승인된 실발송 테스트를 한다. 서비스 워커 HTTPS, VAPID, FCM 설정과 링크 `/p/{notice_id}`를 확인한다. 프런트 빌드만으로 Edge 함수 런타임이나 실제 기기 수신은 검증되지 않는다.
6. pg_cron/pg_net/Vault가 준비되면 Vault에 `recruitment_alerts_url`, `recruitment_alerts_cron_secret`을 안전하게 등록한다. `supabase/manual/schedule-recruitment-alerts.sql`은 수동 실행용이며 기존 동일 이름 작업이 있으면 중단한다.
7. 준비 후 `RECRUITMENT_ALERTS_ENABLED=true`로 활성화하고 큐/함수 오류/예약 실행 결과를 모니터링한다. 필요 시 false로 즉시 발송을 중지한다. Firebase Hosting 배포는 별도 사용자 승인 필요.

## 발송 및 운영 한계

- 서버 시간으로 매분 모집 시작/마감, 공개 여부, 상세 준비, 종료·취소, 계정 차단 및 관심 취소를 확인한다. 최대 20건씩 처리하므로 대기열/기기 상태에 따라 늦어질 수 있으며 정각 수신 보장은 없다.
- 행의 revision/attempt로 원자적 발송 선점을 한다. 바로 발송 직전 다시 적격 여부를 확인하며 일정이 미뤄졌으면 선점을 해제한다. 이미 전송이 시작된 푸시는 취소로 회수할 수 없다.
- 명시적 FCM 429/500/503은 지수 지연으로 최대 5회까지 시도한다. 네트워크 시간 초과처럼 수락 여부 불명은 uncertain, 성공 후 DB 기록 실패/프로세스 중단은 sending에 남겨 자동 재발송하지 않는다. 관리자가 원인을 확인해야 하며 전달의 exactly-once 보장은 아니다.
- FCM 수락(sent)은 기기 수신을 보장하지 않는다. 알림 권한 철회/토큰 만료/네트워크/운영체제 제한이 있을 수 있다. 전송 tag/topic으로 중복 표시를 줄이고 TTL은 모집 마감 또는 1시간 중 짧은 값이다.
- 이미 발송한 같은 프로그램 알림은 다시 신청해 재발송하지 않는다. 모집 재개에 대한 반복 알림은 별도 요구사항이다.
- 관심 취소는 행을 삭제하지 않고 disabled로 보존한다. 실패·오래된 토큰의 보존 기간/관리자 정리 정책은 운영 결정이 필요하다.
