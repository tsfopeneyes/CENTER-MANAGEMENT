# 로그인·현재 화면 재확인 서버 진행 — 2026-08-31

운영 DB·계정·설정·배포·기존 화면은 변경하지 않았다. 전체 인증 전환의 서버 구현 단계이며,
실제 Supabase 운영 로그인이나 이용자 기기 인증을 전환한 결과가 아니다.

## 이번에 구현한 동작

- `loginService.mjs`: 초기 로그인과 프로필 선택 후 재확인을 같은 검증 경로로 처리한다.
  프로필 ID는 선택 조건일 뿐 인증 근거가 아니다. 역할/이메일/Auth ID를 입력으로 받지 않는다.
- `passwordGateway.mjs`: 서버가 선택한 로그인 이메일과 입력 비밀번호를 Supabase 표준
  비밀번호 로그인에 전달한다. 비밀번호 해시 제출·자동 재시도·자체 파생 비밀번호는 사용하지 않는다.
- `loginStore.mjs`: 보호된 회원 연결/로그인 식별자 조회, DB의 원자적 시도 제한,
  비밀번호 확인 뒤 최신 계정 상태를 잠그고 재검사한 후 신뢰 근거 저장.
- `loginHandler.mjs`: 제한된 JSON POST, 허용 Origin, 4KB 본문 한도, 기본 10초 제한,
  일반화된 실패 응답. 성공 응답에만 해당 계정의 세션 토큰을 반환하고 비밀번호/이메일/후보 명단은
  반환하지 않는다. 기존 세션 토큰은 요청받거나 폐기하지 않는다.
- `accountAuthService.mjs`: `/login`, `/session`을 연결하는 명시적 구성 함수.
  운영 진입점/자동 실행/환경변수 읽기는 없고, 실제 배포 준비 검증을 주입하지 않으면 로그인 거부.
- 검토용 `auth-login-foundation.sql`: 보호된 로그인 식별자·시도 횟수와 서버 역할.
  기존 회원 데이터/비밀번호 가져오기나 실제 자격 전환은 없으며 자동 migration과 분리했다.

비밀번호는 DB에 추가 저장하지 않는다. 이름/전화번호 조회 및 시도 제한 키에는 서버 비밀값을
사용한 HMAC을 쓴다. 이 값은 조회용이며 비밀번호 파생/검증용이 아니다. 실제 운영 비밀값을
생성하거나 설정하지 않았고 테스트는 고정 가상 값만 사용한다.

동명이인 후보가 여러 명이면 임의 선택하거나 여러 사람의 비밀번호 로그인을 차례로 시도하지 않는다.
이름+비밀번호로 식별이 유일한 경우는 그대로 처리하고, 등록 전화번호를 추가한 식별도 지원한다.
이름/학교/전화번호 후보 목록은 반환하지 않는다. 최종 동명이인 입력 UI는 아직 연결하지 않았다.

기존 자격은 기본 `legacy_pending`, 비활성 상태다. 검증 없이 `supabase_password`로 바꾸지 않는다.
이전 공개 해시가 실제 Auth 비밀번호인 계정을 새 안전 기준으로 간주하지 않는다.

## 실패·경쟁 상황 처리

- 로그인/재확인 모두 동일한 계정 시도 제한을 공유한다. 인스턴스 메모리가 아닌 DB의
  조건부 UPSERT이므로 동시에 요청해도 정해진 횟수를 초과해 승인하지 않는다.
- 현재 시험값은 10분당 클라이언트 20회, 입력 식별자 10회, 계정 5회다. 운영 활성화 전
  센터 공용망·키오스크 이용량과 오탐 가능성을 확인해 제한을 확정해야 한다.
- 클라이언트 식별자는 신뢰된 ingress에서 주입해야 한다. 요청 본문이나 검증되지 않은
  X-Forwarded-For를 사용하지 않는다. 실제 ingress 어댑터가 없으면 운영 연결하지 않는다.
- 비밀번호 검증 도중 연결/Auth ID/로그인 이메일/자격 버전/정지/초기화 상태가 바뀌면 거절한다.
- 로그인 식별자의 변경/삭제는 새 보호 테이블의 트리거로 자격 버전을 증가시킨다.
  식별자 소유 회원을 다른 사람으로 재지정하는 UPDATE는 거절한다.
- 폐기되었거나 기존에 존재하는 세션 신뢰 근거를 덮어쓰거나 되살리지 않는다.
- 실패/취소/시간 초과 시 그 시도에서 새로 받은 세션만 scope=local로 정리를 시도한다.
  원래 기기의 세션이나 다른 기기 세션을 일괄 로그아웃시키지 않는다.
- Auth 생성 응답이나 DB COMMIT 결과가 유실될 수 있으므로 자동 로그인 재시도는 하지 않는다.
  새 세션 정리가 실패할 가능성은 남는다. 토큰을 실패 응답에 넣지 않으며, 신뢰 근거와 실제
  활성 세션을 함께 검사한다. 운영 전 미완료 처리 관찰/정리 절차도 마련해야 한다.
- 임시 비밀번호 상태는 올바른 비밀번호를 확인해도 일반 세션을 반환하지 않는다.
  변경 전용 서버 코어와 격리 SQL은 추가했다. 실제 연결 및 정책 검증은 아직 남아 있다.
  자세한 범위는 `docs/auth-credential-server-progress.md` 참고.

## 검증

`node scripts/test-login-service.mjs` 통과:

- 실제 loopback HTTP에서 로그인 → DB 신뢰 근거 저장 → 공통 클라이언트/서버 인증 확인까지 연결.
- 이름 중복·추가 전화번호 식별·잘못된 비밀번호·해시 제출·역할/ID 주입 거절.
- private 테이블의 anon/authenticated 접근 거절. 로그인 worker의 public.users/Auth 비밀번호
  변경 및 Auth 비밀번호 열 조회 거절. 원본 회원·Auth 사용자 행 내용 유지.
- 최초 비밀번호 확인과 저장 사이의 계정 버전/상태/이메일 변경을 주입해 저장 거절 검증.
- 로그인/재확인 합산 제한, 같은 제한 키의 동시 20개 요청 중 5개만 허용되는 SQL 검사.
- 잘못된 Auth ID·초기화 후 변경 필요·네트워크 장애·미준비 서버 거절.
- 시간 초과 후 늦은 로그인 성공을 반영하지 않고 새 세션 정리. 기존 세션 보존.
- 새 로그인 이후 재확인 실패가 발생해도 이전에 확인된 세션의 공통 인증 검사는 계속 통과.
- 기존 폐기 근거 보존, 연결 반환, 비밀번호/이메일 없는 응답, 잘못된 Origin/과대 입력 거절.

Auth 상위 응답은 가상 제공자다. PGlite는 독립 메모리 DB이며 실제 운영 PostgreSQL의
다중 연결 잠금 성능·Supabase Auth 설정·Edge 환경을 검증한 것은 아니다.
시험에서 fake Auth 제공자의 쓰기는 별도 서비스 권한을 모사하며, 실제 로그인 worker에
auth.sessions 쓰기 권한을 부여하지 않았다.

기존 test-session-continuity, test-session-service, test-auth-link-integrity,
test-interest-confirmation 통과. localhost:5173 격리 화면 HTTP 200 확인.
이번에는 프런트 실행 경로가 바뀌지 않아 전체 Vite 빌드는 반복하지 않았다.

## 남은 전환 조건

1. 가입 인증 준비의 중복 방지·응답 유실 복구 코어를 격리 구현했다
   (`docs/auth-registration-server-progress.md`). 회원 저장 finalizer와 가입 검증 어댑터는 남아 있다.
   초기화·임시 비밀번호 변경 코어는 격리 구현했고,
   관리자 검증 어댑터·네 자리 비밀번호 정책 호환성·미완료 작업 복구 도구·HTTP/UI 연결이 남았다.
2. 브라우저 공통 로그인/재확인/로그아웃 직렬화 코어와 HTTP 연결 시험을 추가했다
   (`docs/auth-client-integration-progress.md`). 실제 SDK 이벤트·입력 보존 UI 연결은 남아 있다.
   실제 앱의 기존 재확인 훅은 아직 이 서버를 사용하지 않는다.
3. 기존 자격 안전 전환·회원 연결 감사·보호 데이터 조회/쓰기 RLS·관리자 MFA와 권한 확인.
   상태 판정 성공만으로 관리자 권한을 주지 않는다.
4. 실제 ingress 식별, 관찰/시도 제한 튜닝, 응답 시간에 의한 계정 존재 추측 위험 검증,
   중단/COMMIT 응답 유실/세션 정리 실패 복구 절차.
5. 조회 키 비밀값의 안전한 생성·백업·복구/교체 절차. 명시적 세션 신뢰 유효기간 정책 확정.
   현재 테스트는 1일이며 운영 값은 설정하지 않았다. 이 값과 SDK 토큰 갱신 주기는 별개다.
6. 최신 백업 및 전체 서비스 복구 시험, 변경 목록/이용자 영향 검토 후 운영 승인.
