# 인증 구조 재설계 계획

작성: 2026-08-31. 계획만 작성. 구현·운영 조회·계정 변경·배포는 수행하지 않았다.
이 문서는 보류된 전환안을 그대로 재개하라는 승인이 아니다.

## 목표와 경계

화면의 로그인 상태와 서버가 인정하는 본인을 일치시킨다. 회원 ID, 신청, 포인트,
출입 원본 로그, 당직, 관심 등록의 소유권을 보존한다. 정상 이용 중 반복 입력과
강제 페이지 이동을 없애되, 저장된 프로필만으로 인증을 만들어 내지 않는다.

현재 프로젝트 규칙은 기존 DB 스키마/원본 로그 변경을 금지한다. 구현 초기에는 격리 DB에서
설계·SQL·검증만 준비한다. 운영 권한/스키마 변경이 필요하면 정확한 변경 목록과 보존 증거를
제시하고 해당 범위의 명시적 승인을 받은 뒤에만 적용한다. Firebase 배포도 별도 승인 대상이다.

## 확인한 출발점

- 현재 verifiedProfileLogin은 ensure-auth-link와 기존 비밀번호 호환 경로를 사용한다.
- 하트는 Supabase 세션의 Auth ID, 여러 기존 화면은 저장된 회원 정보를 사용한다.
- 가입은 Auth와 회원 저장이 나뉘며, 이전 조사에서 일부 실패·재시도 복구의 공백이 확인됐다.
- 과거 기록의 임시 회원 12명은 정식 회원의 로그인 장애 사례가 아니다.
- 최신 기록상 암호화 백업과 계정 테이블 복원 시험은 성공했다. 전체 DB·권한·서비스 복원
  시험까지 완료한 것은 아니다. 과거 계정 수를 현재 세션 부재 인원으로 해석하지 않는다.
- 보류된 전환안은 전체 재로그인, 자체 자격 증명 파생, 서버 세션 목록을 포함한다.
  자동 복원하지 않고 필요한 부분만 재검토한다.

## 권장 구조

1. Supabase Auth를 세션 발급·갱신의 단일 기반으로 사용한다. 자체 토큰 발급 체계는 추가하지 않는다.
2. 회원 프로필은 업무상 회원 ID를 유지한다. Auth ID와 회원 ID의 연결은 서버가 관리하고,
   브라우저가 연결·역할·정지 상태를 변경할 수 없게 한다. 원칙은 정식 회원과 Auth의 1:1 연결이며
   게스트/임시 기록에는 Auth를 강제로 만들지 않는다. 소유권 미확인 연결은 자동 병합하지 않는다.
3. 이름+비밀번호 UX는 초기 유지안이다. 이름은 식별 보조값이며 인증 근거가 아니다.
   서버의 제한된 로그인 진입점에서 검증하고, 검증 전 동명이인 학교·연락처 목록은 노출하지 않는다.
   비밀번호가 일치하는 후보도 중복이면 추가 식별 절차를 사용하며 임의로 첫 계정을 선택하지 않는다.
4. 새 자격 증명은 Supabase Auth가 관리하는 표준 저장을 우선한다. 공개 users.password,
   브라우저 비밀번호 해시 검증, 해시 자체를 로그인 비밀번호로 사용하는 경로는 최종적으로 제거한다.
   이전 해시가 필요한 과도기는 서버 전용·접근 제한·폐기 조건을 둔다. 노출 가능성에 따라 기존
   비밀번호 유지 가능성을 별도로 판단한다. pepper 파생/이중 비밀번호 저장은 기본안으로 재사용하지 않는다.
5. AuthProvider와 공통 인증 클라이언트 한 곳에서 앱의 인증 상태를 관리한다.
   캐시된 회원 정보는 표시용이며 권한 근거가 아니다. API는 검증된 세션과 서버 연결을 사용한다.
6. 서버 API와 DB RLS가 실제 권한을 강제한다. UI 숨김이나 getSession 결과만으로 권한을 승인하지 않는다.
   관리자 권한은 서버가 관리하며, 비밀번호 변경·권한 변경 등 민감 작업은 현재 세션/폐기 상태도 확인한다.

현재 React SPA와 직접 Supabase 접근을 유지하는 안을 우선한다. SDK 토큰 저장소는 별도로 복제하지
않고 비밀번호/해시/토큰 로그를 금지한다. HTML 정화, 스크립트 삽입 경로, CSP, 의존성 점검을 포함한다.
HttpOnly 쿠키로 옮기려면 서버 중계 구조와 CSRF 방어까지 필요하므로 단순 저장 위치 변경으로 취급하지 않는다.

## 앱 동작 계약

| 상태 | 화면과 동작 |
| --- | --- |
| 최초 확인 중 | 인증 확인 표시. 보호 데이터 조회·저장은 대기 |
| 인증 및 회원 연결 확인 완료 | 모든 기능이 같은 계정으로 동작 |
| 갱신 중 | 현재 화면과 입력 유지. 중복 갱신을 합치고 보호 요청은 대기 |
| 일시적 통신 실패 | 세션을 삭제하거나 로그아웃시키지 않음. 재시도 안내, 보호 저장은 보류 |
| 인증 복구 불가 | 공통 본인 확인 창. 확인 후 계정이 같을 때 원래 작업 재개 |
| 연결 충돌/정지 | 자동 연결·다른 계정 저장 금지. 원인을 구분해 복구 안내 |
| 명시적 로그아웃 | 해당 계정 캐시/민감 임시 입력 제거. 다른 회원 데이터가 남지 않게 처리 |

여러 탭·앱 복귀·휴대폰 절전 후 복귀를 동기화한다. 계정 변경 중 도착한 이전 요청은 폐기한다.
화면 복귀 시 무조건 로그인하지 않으며, 갱신 재시도에 한도를 둔다. 쓰기 요청은 응답 유실 시
무조건 재전송하지 않고 중복 방지 키 또는 저장 결과 조회로 확인한다. 인증 재확인 후에도
모집 종료·정원·권한을 다시 검사한다. 입력 보존은 비밀번호 영구 저장을 의미하지 않는다.

## 구현 순서와 통과 조건

### 1. 현황·권한·전환 범위 확정

- 로그인/가입/비밀번호/관리자/게스트/키오스크/QR/알림/Storage/Realtime/RPC 경로를 목록화한다.
- 익명, 본인, 타 회원, 스태프, 관리자, 키오스크의 읽기/쓰기 권한 표를 만든다.
- 코드의 모든 직접 테이블 접근과 RPC fallback을 함께 검토한다. fallback에도 동일한 RLS·권한을
  적용하고 권한 거부 시 우회하지 않는다. 안전한 직접 fallback이 불가능한 작업은 보호된 서버
  API로 설계하며, 원자적 작업을 브라우저의 여러 쓰기로 대신하지 않는다.
- 기존 연결 무결성과 인증 경로 신뢰성을 읽기 전용으로 점검하는 도구를 준비한다.
  세션 부재 인원은 회원 수로 추정하지 않는다. 필요 시 별도 승인한 최소 진단 집계로 측정한다.
- 산출물: 경로 목록, 권한 표, 세션 유지 가능 조건, 운영 변경 예상 목록.

### 2. 독립 환경에서 인증·회원 연결 구현

- 이름 로그인 서버 진입점, 표준 Auth 연결, 공통 상태 관리와 갱신 처리를 구현한다.
- 가입에는 요청 ID와 처리 상태를 두어 재시도 시 같은 계정을 이어서 완성한다.
  Auth 생성 후 회원 저장 실패 등 단계별 장애를 재현한다. 자동 삭제·새 계정 반복 생성은 하지 않는다.
- 가입, 게스트 승급, 복구, 향후 병합을 같은 연결 규칙 아래 둔다. 병합은 별도 검증 전 중지 유지.
- 계정/IP 등 공유 제한, 일반화된 오류 응답, 비밀값 없는 감사 기록을 적용한다.
- 산출물: 격리 DB에서 검증한 서버와 재시도/복구 도구. 운영 데이터는 사용하지 않는다.

### 3. 공통 인증을 모든 기능에 연결

- 로그인/학생/관리자 화면부터 하트·신청·프로필·당직·알림·업로드·채팅 순으로 전환한다.
- 하트 전용 인증 구현은 공통 본인 확인 흐름으로 흡수한다.
- 공개 캘린더와 공개 프로그램은 로그인 없이 유지한다. 키오스크에는 전용 최소 권한을 주고,
  게스트 기록을 일반 회원 세션으로 가장하지 않는다. 관리자의 학생 미리보기는 본인 전환이 아니다.
- 로컬 localhost:5173에서 실제 컴포넌트와 격리 응답/시험 서버로 검증한다.

### 4. 권한·비밀번호 복구 완성

- 회원 전체 공개 읽기/쓰기, 역할·Auth 연결 변경, 비밀번호 확인값 노출 경로를 닫는 변경안을 준비한다.
- DB, 뷰, RPC, Storage, Realtime, 서버 서비스 권한 모두 검사한다.
- 사용자 확인 사항: 관리자가 직접 본인 확인한 뒤 등록된 전화번호 뒤 4자리로 초기화하는
  운영 방식을 유지한다. 본인 확인은 초기화 요청자의 신원을 확인하는 절차이며, 네 자리 값의
  추측 위험을 없애지는 않으므로 영구 비밀번호가 아닌 제한된 임시 비밀번호로 설계한다.
- 초기화는 서버가 검증한 관리자만 실행하고 서버에 등록된 번호를 사용한다. 브라우저가 보낸
  번호는 신뢰하지 않는다. 번호가 없거나 확인되지 않으면 초기화를 거부하고 별도 복구로 안내한다.
- 임시 비밀번호는 짧은 유효기간과 계정별 공유 시도 제한을 적용한다. 성공하면 비밀번호 설정만
  가능한 제한 상태로 전환하고, 새 비밀번호 설정 전 일반 데이터/API 접근을 서버·RLS에서 막는다.
  동일한 뒤 네 자리를 새 비밀번호로 다시 설정할 수 없게 한다. 구체적 유효기간·시도 한도는
  구현 전 확정하며, 반복 초기화로 시도 제한을 우회할 수 없게 한다.
- 초기화 시 기존 세션을 폐기하고, 실행 관리자·대상 계정·시각·결과만 감사 기록에 남긴다.
  비밀번호·전화번호 원문은 로그에 남기지 않는다. 폐기 전 JWT의 접근 차단도 아래 정책으로 검증한다.
- 관리자 MFA와 복구 절차를 준비하고 권한 상승·초기화 작업에 추가 확인을 적용한다.
- 이전 JWT는 비밀번호 변경/로그아웃만으로 즉시 모두 무효화된다고 가정하지 않는다.
  민감 작업은 서버의 폐기 검사를 적용하고 나머지는 실제 토큰 수명과 노출 허용 범위를 명시한다.

### 5. 전환·복구 리허설

- 새 시점의 암호화 백업과 복구 수단을 검증한다. 이전 성공분은 재사용 가능 여부부터 확인해
  불필요한 도구 재개발·비밀번호 반복 입력을 피한다.
- 계정 테이블뿐 아니라 정책·함수·트리거·Storage 참조·핵심 기능 복구를 시험한다.
- 가입/비밀번호 변경의 중단 지점을 주입하고 재개·중복 방지를 검증한다.
- 회원/신청/포인트/출입/당직/관심의 ID·내용·연결 비교 기준을 만든다. 정상 신규 기록 증가는
  전환 오류와 구별한다. 전환 중 가입/계정 변경 정지 범위와 최대 시간을 실측한다.
- 운영과 같은 시험 환경의 서버/DB/클라이언트 호환 조합 및 오래된 탭·서비스 워커를 시험한다.

### 6. 검토 가능한 결과를 제시한 뒤 운영 승인·적용

- 승인 요청 전에 변경 SQL, 대상 기능, 영향 범위, 유지/재확인 대상 판정, 복구 절차,
  리허설 결과, 예상 중단 시간을 제공한다. 지금 단계에서 전원 무중단을 약속하지 않는다.
- 서버와 권한 준비 상태를 확인한 뒤 화면을 활성화한다. 서버가 없는데 화면부터 연결하지 않는다.
- 기능별 시험 공개는 가능하지만 위험한 옛 인증 경로를 함께 열어 두는 방식은 허용하지 않는다.
- 기존 세션은 서명/만료뿐 아니라 과거 발급 경로와 회원 연결까지 신뢰 가능한 경우만 유지한다.
  불가능하면 현재 화면에서 본인 확인한다. 보안상 광범위 재확인이 불가피하면 승인 전에 설명한다.
- 실패 시 활성화를 중단하고 보호 쓰기를 막는다. UI 되돌리기는 안전한 API와 호환될 때만 허용한다.
  공개 비밀번호·약한 RPC를 되살리는 롤백이나 운영 신규 기록을 덮는 전체 복원은 하지 않는다.
- 승인된 시험 계정만으로 실제 확인하며 다른 이용자에게 시험 알림을 보내지 않는다.

- 화면과 서버가 서로 다른 회원을 사용하지 않음. 프로필/역할 위조, 타인 ID 지정, 이전 계정의
  늦은 응답, 폐기된 민감 작업 세션이 모두 거절됨.
- 자정/시간 경과/재시작/복수 탭/절전 복귀/오프라인에서 갱신과 재연결이 예측대로 동작함.
- 하트·신청·가입 재시도에 중복이 없고 실패를 성공으로 표시하지 않음.
- 기존 핵심 기능과 데이터 연결 유지, 비공개 프로그램·개인 알림·개인 파일 권한 검사 통과.
- 비밀번호/해시가 공개 API·브라우저 회원 캐시·로그·배포 산출물에 없음.
- 기존 로컬 단위 테스트에 더해 실제 Supabase 시험 환경의 RLS/SDK/Edge 검증과 모바일 UI 검증 통과.
- 배포 후 인증/갱신 실패율, 연결 오류, 가입 미완료, 보호 작업 오류를 비밀값 없이 관찰하고
  리허설에서 정한 기준 초과 시 확대 중단. 통과 전에는 보안 전환 완료로 선언하지 않음.
