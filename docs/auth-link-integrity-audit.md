## 확인한 생성 결함과 수정

기존 ensure-auth-link는 auth_user_id가 없으면 profile.id에 이미 존재하는 Auth를 조회하지 않고 전화번호 기반 주소로 새 Auth를 생성했다.
신규 연결 주소를 전화번호로 추측하여 반환하므로 기존 UUID 주소의 인증 계정을 재사용할 수 없었다.
프런트 로그인도 어느 쪽으로든 성공하면 받아들이거나 일부 분기에서 회원과 Auth ID 일치를 확인하지 않았다.
실제 두 중복 계정의 과거 생성 요청 로그까지 입증한 것은 아니므로 개별 생성 원인 확정과 코드 결함 확인은 구분한다.

수정 파일:
- `supabase/functions/dispatch-notification/auth-link.mjs`: 기존 직접 ID 및 명시적 연결 ID 조회, 기존 실제 이메일 반환, 새 계정 생성 전 전체 페이지 후보 확인.
- 확인된 기존 연결은 유지하며 중복 자동 병합 금지. 연결 유실·조회 오류·다른 회원 소유·단순 연락처 일치 후보는 새 계정 생성 없이 중단.
- 실제 새 인증이 필요한 경우에는 회원 ID 기반 고정 이메일과 서버 전용 app_metadata 표식 사용. 동시 요청의 이메일 중복 및 생성 후 프로필 저장 실패는 같은 Auth를 복구·재사용한다.
- 프로필 연결 저장은 NULL 조건부 갱신. 이미 다른 연결이 들어오면 덮어쓰지 않는다.
- 게스트/임시 기록의 로그인 시 자동 인증 생성 금지.
- `src/utils/verifiedProfileLogin.js`, GuestMobileWelcome: 서버가 선택한 인증 계정으로 로그인하고, 반환된 ID와 실제 로그인 ID가 정확히 일치해야 성공. 불일치 시 로컬 Auth 세션 해제.

이 수정은 기존 로그인 방식을 새 account-auth 서비스로 전환하지 않는다. 기존 공개 회원 권한/비밀번호 저장 구조 전체의 보안 개선이 완료됐다는 뜻도 아니다.
신규 가입의 Auth 생성→회원 INSERT 부분 실패, 게스트 승급, 계정 삭제/병합의 기존 문제는 별도 조사 문서 `account-auth-link-investigation.md`에 남아 있다. 이 패치는 로그인 연결 경로의 중복 생성 방지 범위다.

## 남은 운영 조치 — 승인/보존 확인 필요

1. 새 프런트는 서버 응답 auth_user_id가 필요하므로 서버 함수를 먼저 배포하고 화면을 나중에 배포한다. 현재 운영 서버는 예전 응답 계약이므로 화면만 먼저 배포하면 로그인 실패한다.
2. 중복 계정은 기존 회원 ID와 업무 기록을 유지하고, 현재 auth_user_id를 우선 유지하는 안이 관심 등록 이동을 최소화한다. 과거 세션은 재로그인이 필요할 수 있다.
3. 제거 후보의 MFA/패스키/OAuth·스토리지 소유권·권한·세션 및 비외래키 참조를 추가로 확인한 뒤 계정별 확정한다. 단순 Auth 삭제는 identities/sessions/MFA 및 관리자 권한에 CASCADE 영향이 있다. 알림 신청 FK는 삭제를 막는다.
4. 승인된 백업 복구 가능 상태를 재확인한 후에만 기존 중복 계정 정리를 수행한다. 이번에는 어떤 Auth도 삭제하지 않았다.
