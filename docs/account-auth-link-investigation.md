# 계정 연결 유지 실패 조사 — 2026-08-31

후속 정정: 로그인 정보 없는 프로필 12개는 전원 preferences.is_temporary=true로 확인됐다.
이용자 목록 기준 게스트/임시이며 정식 회원의 로그인 장애 사례로 취급하면 안 된다.
아래 코드 결함은 별도로 존재하지만 이 12명이 그 결함으로 생성됐다는 증거는 아니다.

운영 데이터는 READ ONLY/ROLLBACK 조회만 수행했다. 계정 수정·삭제·로그인 차단·배포는 하지 않았다.

## 확인한 구현 결함

1. Git HEAD의 `src/components/auth/hooks/useSignUp.jsx` 166–180행은 Auth 가입 후
   같은 ID로 회원을 별도 저장한다. 회원 저장이 실패하면 오류만 표시하고, 이미 만든 Auth의
   재시도/복구 처리는 없다. 이 방식은 2026-03-30 커밋 `f90552e`에도 존재한다.
   저장된 소스의 증거이며, 각 계정 생성 당시 배포 버전을 확정하는 증거는 아니다.
2. 관리자 회원 삭제(`src/components/admin/users/hooks/useAdminUsers.jsx`)는 public.users만 삭제한다.
   Git HEAD의 `src/api/userMergeApi.js` 직접 병합 대체 경로 역시 원본 프로필만 삭제하고 Auth를
   이전/정리하지 않는다. 현재 로컬 병합 API는 이미 중지되어 있으나 운영 적용은 하지 않았다.
3. 운영 `merge_guest_to_member`는 새 프로필 삽입·기록 이동 후 기존 프로필만 삭제한다.
   운영 `merge_duplicate_users`는 같은 ID의 Auth도 삭제하므로 그 정상 실행 경로 자체를
   Auth 잔존 원인으로 단정하면 안 된다. 별도 auth_user_id는 이 함수에서 처리하지 않는다.
4. 운영 `upgrade_guest_account`는 기존 Auth를 UPDATE만 한다. Auth가 없어도 영향 행 수를
   확인하지 않고 회원 업데이트 후 true를 반환한다. 따라서 회원만 정식 가입 상태가 될 수 있다.
   기존 브라우저 코드의 RPC 실패 대체 경로도 회원 테이블만 업데이트한다.
5. 운영 auth.users/public.users에 사용자 정의 트리거는 없다. public.users의 제약은
   PRIMARY KEY(id), UNIQUE(auth_user_id)이며 Auth 연결을 보장하는 외래 키는 조회되지 않았다.
   UNIQUE만으로는 두 저장의 성공이나 삭제 후 연결 유지를 보장하지 않는다.

## 실제 미연결 12개의 단서

- 7개: UUID@youth-access.app 형식, UUID는 각 Auth ID와 같다. 모두 3월 27일 약 2.211초
  사이 생성됐다. 이전 일괄 생성 가능성을 시사하지만 실행 이력은 확인하지 못했다.
  해당 UUID의 현재 회원은 없다. 이 단서만으로 삭제됐다고 확정할 수 없다.
- 5개: 전화번호@youth-access.app 형식으로 기존 신규 가입 코드의 형식과 일치한다.
  전화번호는 반환하지 않고 DB 내부에서 정규화 비교했으며 현재 회원 전화번호 일치 후보는 0개다.
- 이름 메타데이터 및 현재 회원 ID/이메일 비교에서도 연결 후보가 없다.
- 생성·로그인 시각은 회원 저장 성공이나 회원 삭제 실행의 증거가 아니다.
  특히 Auth 로그인 시각만으로 서비스에서 회원 로그인이 완료됐다고 판단하지 않는다.

## 결론과 제한

가입 시 같은 ID를 쓰도록 구현했지만, 가입의 일부 실패·회원 삭제·병합·게스트 승급 전 과정에서
연결을 유지하는 처리가 빠져 있었다. 미연결 상태를 만들 수 있는 구체적 결함은 확인했다.
개별 12개에 어떤 경로가 실행됐는지까지 입증할 과거 회원 변경 이력은 이번 조회로 확보하지 못했다.
원인을 12개 모두에 확정 적용하거나 이 증거로 자동 연결/삭제하면 안 된다.

새 로컬 서버 코드도 Auth 생성→프로필→자격 정보 저장이 나뉘어 있다.
`service.mjs` register와 `store.mjs` insertRegistration은 일부 실패를 보존하지만
자동 복구/재시도 완료까지 구현한 상태는 아니다. 서버로 옮겼다는 이유만으로 재발 방지가
완료됐다고 설명해서는 안 된다. 배포 전 가입 실패의 복구 및 재시도 설계를 보완하고 검증해야 한다.
